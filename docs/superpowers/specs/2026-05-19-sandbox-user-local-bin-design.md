# Sandbox User-Local Binary Environment Design

Date: 2026-05-19

## Problem

OpenShell agents can fetch public internet resources under `network_policy: permissive`, but installs still fail when tools try to write global binaries or package state into root-owned locations. One observed case is `npm install -g`, which defaults to the Node installation prefix and can require sudo. A second observed case is a manually installed binary being placed in `~/bin`, while Right Agent's existing convention already expects agent-installed CLI tools under `/sandbox/.local/bin`.

The platform needs one explicit, self-healing user-local binary contract for sandboxed agents:

- agents should know where to place manually downloaded CLIs;
- npm global installs should write into a writable user prefix;
- binaries should be immediately available to current Claude invocations and later interactive SSH shells;
- the contract should be regenerated by Right Agent, not manually repaired inside sandboxes.

## Goals

- Use `/sandbox/.local/bin` as the canonical location for user-installed executable files.
- Configure npm global installs to use `/sandbox/.local` as their prefix, making global npm bins land in `/sandbox/.local/bin`.
- Configure npm cache to use `/sandbox/.npm`.
- Make this environment available to every sandboxed `claude -p` invocation, including non-login SSH commands.
- Make the same environment available to user SSH shells through `/sandbox/.bashrc`.
- Update the generated OpenShell system prompt so agents are told to install user CLIs into `/sandbox/.local/bin`, not `~/bin`, and to avoid sudo for installs.
- Keep the implementation self-healing for existing sandboxes.

## Non-Goals

- Do not support multiple canonical bin directories.
- Do not bless `/sandbox/bin` or `~/bin` as supported install locations.
- Do not modify unsandboxed agents beyond any shared helper code needed for clean implementation.
- Do not manually patch existing sandboxes as a recovery step.
- Do not change OpenShell filesystem policy unless implementation proves the current policy blocks the chosen paths.

## Chosen Approach

Use a generated managed shell init file:

```sh
/sandbox/.right/env.sh
```

Right Agent owns this file and may overwrite it on startup. `/sandbox/.bashrc` should contain only a guarded source block for the managed file, instead of duplicating environment exports directly.

The managed file exports:

```sh
export PATH="/sandbox/.local/bin:$PATH"
export NPM_CONFIG_PREFIX="/sandbox/.local"
export NPM_CONFIG_CACHE="/sandbox/.npm"
```

The sync layer also ensures these directories exist:

```text
/sandbox/.right
/sandbox/.local/bin
/sandbox/.npm
```

This keeps `/sandbox/.local/bin` as the single executable convention for both npm-installed CLIs and manually downloaded binaries.

## Runtime Flow

At bot startup, after the sandbox is ready and before any Telegram handling starts:

1. `initial_sync` runs.
2. The sync layer writes `/sandbox/.right/env.sh`.
3. The sync layer ensures `/sandbox/.bashrc` sources `/sandbox/.right/env.sh`.
4. Existing platform sync continues to deploy managed files and verify `.claude.json`.

For every sandboxed Claude invocation:

1. The SSH command runs a generated shell script.
2. That script sources `/sandbox/.right/env.sh` before assembling the system prompt and before running `claude -p`.
3. If the env file is missing for any reason, the invocation exports the same baseline values inline so a recoverable turn is not blocked by a missing generated file.

For user SSH access:

1. `right agent ssh <agent>` opens a shell whose `.bashrc` sources `/sandbox/.right/env.sh`.
2. `npm install -g <pkg>` uses `/sandbox/.local`.
3. Manually installed CLIs should be moved or installed into `/sandbox/.local/bin`.

## System Prompt Changes

Only OpenShell agents should receive this extra environment guidance. The generated base system prompt should add this short block inside `## Environment`, directly after the home directory line:

```text
User-installed CLI tools:
- Put manually installed executables in `/sandbox/.local/bin`.
- `/sandbox/.local/bin` is on PATH for your sandbox sessions.
- Do not install tools into `~/bin`; use `/sandbox/.local/bin`.
- Do not use sudo for tool installs.
- npm global installs are configured with `NPM_CONFIG_PREFIX=/sandbox/.local`, so `npm install -g <pkg>` exposes bins in `/sandbox/.local/bin`.
- npm cache is configured at `/sandbox/.npm`.
```

The prompt should not claim these locations exist for `sandbox.mode = none`, because no-sandbox agents run in the host agent directory and should not be told to write to `/sandbox`.

`PROMPT_SYSTEM.md` must be updated to match the generated prompt.

## Implementation Shape

Expected code areas:

- `crates/bot/src/sync.rs`
  - replace the narrow `ensure_local_bin_in_path` behavior with a managed env file deployment and `.bashrc` source check;
  - keep the function idempotent;
  - avoid fragile `sed` replacement of a specific PATH line.
- `crates/bot/src/cc/prompt.rs`
  - ensure sandboxed prompt assembly scripts source `/sandbox/.right/env.sh` or inline the same env fallback before running `claude -p`.
- Sandbox invocation callsites
  - worker, cron, async delivery, reflection, and background invocation paths already call `build_prompt_assembly_script`; prefer centralizing this behavior there.
  - background learned-skill review has a direct SSH command path and must receive the same env setup if it bypasses prompt assembly.
- `crates/right-codegen/src/agent_def.rs`
  - update generated system prompt for OpenShell agents.
- `PROMPT_SYSTEM.md`, `ARCHITECTURE.md`, and `docs/architecture/sandbox.md`
  - document the user-local binary contract and managed env file.

## Testing

Follow TDD.

Regression tests should cover:

- generated env file content includes `PATH`, `NPM_CONFIG_PREFIX`, and `NPM_CONFIG_CACHE`;
- `.bashrc` source block is idempotent and does not duplicate on repeated sync;
- prompt assembly script sources or falls back to the managed env before `claude -p`;
- OpenShell system prompt includes user-local binary guidance only for sandboxed agents;
- no-sandbox system prompt does not mention `/sandbox/.local/bin`;
- background learned-skill review command gets the same sandbox env setup if it uses a direct SSH command.

Live or ignored OpenShell test, if practical:

- start a disposable sandbox through the generated flow;
- verify `bash -lc 'printf "%s\n" "$NPM_CONFIG_PREFIX"; npm prefix -g'` reports `/sandbox/.local`;
- verify `bash -lc 'case ":$PATH:" in *:/sandbox/.local/bin:*) exit 0;; *) exit 1;; esac'`;
- optionally verify `npm install -g <small-cli>` places a bin under `/sandbox/.local/bin` when network is available.

Final verification for implementation must include:

```sh
devenv shell -- cargo fmt --check
devenv shell -- cargo test --workspace
devenv shell -- cargo build --workspace
```

## Rollout

This is an upgrade-friendly change. Existing sandboxes should pick it up on bot restart through `initial_sync`; no sandbox deletion or recreation should be required.

The current manually installed binary in `~/bin` should not drive the platform contract. After rollout, agents will be instructed to use `/sandbox/.local/bin`. Existing `~/bin` contents may remain untouched unless a future migration proves there is real user data that must be preserved.

## Open Questions Resolved

- Canonical bin path: `/sandbox/.local/bin`.
- npm prefix: `/sandbox/.local`.
- npm cache: `/sandbox/.npm`.
- Compatibility path for `~/bin`: not supported as a platform convention.
