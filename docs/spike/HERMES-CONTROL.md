# Round-10 Report: Does Hermes use structured output? — and is tool-call-as-control the model-robust primitive RightClaw should adopt?

## 1. Direct answer

**No — Hermes does not force a json-schema structured-output envelope on the agent turn. Its control primitive is native function-calling (tool-calls-as-control) plus a plain-text reply, with a free-text sentinel for the one decision that needs no schema.** Verified by direct grep of cloned source (NousResearch/hermes-agent @ `8cf9d86`): the two turn-path modules — `agent/conversation_loop.py` (4252 lines) and `agent/chat_completion_helpers.py` (2682 lines) — contain **zero** case-insensitive occurrences of `response_format`, `json_schema`, `guided`, or `structured_output`, and the sole chat-completion kwargs builder `build_api_kwargs()` forwards only `tools=tools_for_api` to `.create()` across every API mode (anthropic_messages, bedrock_converse, codex_responses, default chat_completions) [verdict C3]. The model's actionable output is its **tool calls** (dispatched by `tool_call.function.name` + `json.loads(arguments)` in `agent/tool_executor.py` [claim 15]) and its **plain assistant text** (`final_response`, terminal when no more tool_calls [verdict C5]). RightClaw's three structured uses become: (1) reply → plain assistant text auto-delivered by the gateway; (2) cron notify-vs-silent → a free-text sentinel `[SILENT]` [verdict C6]; (3) prefilter classify → a tool call (`skill_manage action=...`) or tolerant free-text JSON parsing [claims C7/C8]. The only `json_schema` in the whole repo's production code sits in `agent/plugin_llm.py`, an explicitly out-of-band plugin lane that calls the payload "a hint that providers may ignore" with best-effort client-side `jsonschema.validate` — never the turn [verdict C4].

## 2. What Hermes is

"Hermes" resolves to **two distinct, related things** [claim 13]:

- **The Hermes MODEL family** (NousResearch Hermes-3 / Hermes-4, Llama/Qwen fine-tunes). Trained for function-calling via a ChatML-embedded XML format and "to produce valid JSON for given schemas and to repair malformed objects" [claim 10, https://huggingface.co/NousResearch/Hermes-4-70B]. Its tool-call text (`<tool_call>{...}</tool_call>`) is converted to OpenAI tool-call objects by the inference server — vLLM `--tool-call-parser hermes` (verified against vLLM's `hermes_tool_parser.py`, which returns OpenAI `ToolCall`/`FunctionCall` objects), SGLang `qwen25` [verdict 4].
- **NousResearch/hermes-agent** — an open-source (MIT), Python agent **platform**: self-improving learning loop, curator, skills, cron, and a cross-channel messaging gateway (Telegram/Discord/Slack/WhatsApp/Signal) [claim C1, https://github.com/NousResearch/hermes-agent]. This is the **peer category platform** that RightClaw's `AGENTS.md` names alongside OpenClaw — i.e. the direct architectural comparable.

**How they relate:** the agent is **provider/model-agnostic** ("Use any model you want" — Nous Portal, OpenRouter, NovitaAI, NVIDIA NIM, HuggingFace, OpenAI, or your own endpoint [claim C11]). It does **not** parse the Hermes model's `<tool_call>` XML itself; the inference server normalizes that to OpenAI tool-calls, and the agent consumes the normalized objects [claim C10/verdict 4]. So the model's *trained format* and the agent's *control mechanism* are cleanly separated — the agent would run any function-calling model, and Hermes-the-model would run under any harness.

The `run_agent.py` line count *was* verified (5405 lines) but is not load-bearing. The MIT/Python/multi-platform identity *is* verified.

## 3. The control mechanism in detail

**Wire format — native function-calling is primary.** The live loop consumes OpenAI-spec streaming tool-call deltas: it iterates `delta.tool_calls`, **assigns** `tc_delta.function.name` (atomic, not concatenated) and **accumulates** `tc_delta.function.arguments` via `+=` per index slot [verdict 1]. The code carries provider-quirk special-cases — Ollama reuses index 0 for parallel calls (disambiguated by id), and "Some providers (MiniMax M2.7 via NVIDIA NIM) resend the full name in every chunk; concatenation would produce `read_fileread_file`" [verdict 1]. Per-provider adapters translate `tools` to Anthropic (`type:any`) and Gemini shapes [claims 4/14].

**Tool definitions** are delivered as a native OpenAI `type:function` array built by `get_tool_definitions` and passed as `tools_for_api = agent.tools` [claim 12]. The text-format fallback instead renders the *same* OpenAI schema into a system-prompt `<tools>` block.

**Self-parsed-text path is adapter-scoped, not a general recovery layer.** The only content-based tool-call extraction in the entire `agent/` package is `_extract_tool_calls_from_text` / `_TOOL_CALL_BLOCK_RE` in `copilot_acp_client.py`: for the GitHub Copilot ACP adapter, the agent injects the OpenAI tool schema into the system prompt, instructs the model to emit `<tool_call>` blocks "in OpenAI function-call shape", and self-parses them [verdict 3]. **Verdict-mandated corrections:** (a) the source calls this "OpenAI shape," not "the Hermes format"; (b) this ACP path is **unconditional** for that adapter — there is **no runtime capability-detection branch** selecting native-vs-text. So the native-vs-self-parsed axis is **BOTH, selected by configured adapter**, not by dynamic provider probing [verdict 3].

> **CORRECTION (Defect 1 from critique):** an earlier finding [claim C7] asserted a six-parser recovery registry `agent/content_tool_calls.py` (PR #35129) handling Kimi/MiniMax/GLM tool calls emitted as text, "fallback-only when structured `tool_calls` is empty." **This file does not exist in main** (`git ls-files | grep content_tool_calls` → empty at `8cf9d86`; the `kimi_k2`/`minimax_invoke` grep surfaces only plugins and tests, no `agent/` registry). The claim's own evidence flagged "PR 35129 merge to main unconfirmed." **There is no general text-recovery registry in main; the only content-recovery path is the Copilot-ACP regex above.** Every robustness argument that leaned on this registry is corrected below.

**Arg validation/retry — coerce/repair, never reject.** Two layers, both purpose-built for weak open models:
- `model_tools.coerce_tool_args` reads each tool's JSON Schema and coerces string→int/bool/array, with an explicit comment: "Open-weight models (DeepSeek, Qwen, GLM) sometimes emit a `urls` field as the string `https://a.com` when the tool expects … a single-element list; wrapping here avoids a confusing tool failure" [verdict-confirmed claim 8].
- `_repair_tool_call_arguments` (defined in `agent/message_sanitization.py:185`, **called from both turn-path modules** — `chat_completion_helpers.py` and `conversation_loop.py`) fixes truncated/malformed streamed JSON (trailing commas, unclosed braces, Python `None`), falling back to `{}` when unrepairable "so repairable malformations … do not kill the session" [claim 9, corrected location per Defect 4]. (The earlier finding cited a *test* file; the implementation is `message_sanitization.py:185`.)

**Moonshot/Kimi schema sanitizer.** `agent/moonshot_schema.py` rewrites tool schemas because "Moonshot Kimi accepts a stricter subset of JSON Schema … Requests that violate it fail with HTTP 400" [claim C8]. This is the only Kimi-specific robustness mechanism that **does** exist in main.

**Reference-model retry loop.** The separate Hermes-Function-Calling repo validates each call against the schema and, on failure, feeds back a `<tool_response>` error asking the model to retry, `max_depth=5` [claim 11].

**The three control uses, concretely:**
- **(a) Reply** — the final assistant text **IS** the reply, auto-delivered; `send_message` is for *additional/cross-channel* sends. The cron duplicate-skip note tells the model: "Put the intended user-facing content in your final response instead" — the **inverse** of RightClaw's "the-turn-reply-IS-the-JSON-envelope" [verdict 5]. `gateway/delivery.py` sends a plain `str`; no typed-envelope parsing anywhere [verdict 5].
- **(b) Cron notify/silent** — a free-text sentinel: `SILENT_MARKER = "[SILENT]"` (scheduler.py:157); delivery suppressed via `if should_deliver and success and SILENT_MARKER in deliver_content.strip().upper(): should_deliver = False` (scheduler.py:2064 — a **substring** match, so slightly broader than "exactly the marker"); the cron prompt forbids combining `[SILENT]` with content [verdict C6]. **CORRECTION (Defect 2 — was wrongly flagged "contested/UNKNOWN"):** the source resolves the empty-output question in one function (scheduler.py:2062-2081). Empty/whitespace output has **two effects**: line 2063 `should_deliver = bool(deliver_content.strip())` suppresses delivery of a blank message, AND lines 2079-2081 (issue #8585) set `success=False` with error "Agent completed but produced empty response." So empty output is an **accidental soft-failure that also happens to suppress delivery** — it is **not** a deliberate silence signal. Only `[SILENT]` is the deliberate, `success=True` stay-silent decision (verdict 6 and finding C6 are both right about their respective effects; there was nothing to leave UNKNOWN).
- **(c) Prefilter classify** — the curator instructs the model to **call** `skill_manage` with `action=patch/create/delete/keep` (decision = tool-call args) [claim C7-curator]. The dedicated urgency classifier `cron/scripts/classify_items.py` uses **no** structured-output param — it calls `call_llm(task="monitor")` and parses scores from free text via `json.loads` + substring fallback, tolerating "could not parse classifier output" [claim C8]. The central auxiliary entrypoint `call_llm` has **no `response_format` parameter** in its signature [claim C9]. **UNKNOWN:** whether the curator's classification is *always* a tool-call vs sometimes a text convention was only partially traced.

`tool_choice` (auto/required/none) **is** expressible per provider — `required → {"type": "any"}` for Anthropic (anthropic_adapter.py:2386, verified) — so forced-tool turns are *possible* but **opt-in per call, not imposed every turn** [claim 14]. Whether `required` is actually *used* anywhere as per-turn control was **not** confirmed by call-site grep [UNKNOWN]. This matters: `tool_choice:required` is the **same emulated-forcing primitive** the MiMo/Venice spike found unreliable.

## 4. Is it more model-robust than RightClaw's json-schema envelope?

**Honest framing first: the reliability win is confined to the *unforced* decisions; for *forced* ones it relocates the fragility onto exactly the same primitive the spike already broke, plus a parser/sanitizer layer RightClaw would have to build.** Mapping to each spike failure:

| Spike failure (forced-envelope path) | Under Hermes tool-call control | Dodged or relocated? |
|---|---|---|
| **Kimi-K2 / small-Qwen `propertyNames` grammar error (Venice)** | Hermes ships a per-model schema sanitizer (`moonshot_schema.py`) and would send a stricter schema; it does **not** ship a general Kimi text-recovery registry (that file is absent from main). | **Relocated to per-model schema-sanitization — NOT structurally dodged.** Decisive nuance the critique surfaced: the spike (SPIKE-RESULTS.md line 71) calls `propertyNames` an *injected* keyword from "MiMo's `StructuredOutput` tool-schema wrapper / AI-SDK conversion — plausibly sanitizable in a MiMo fork." So the Kimi failure is **not** intrinsic to forced-envelopes-vs-tool-calls; it is a tooling bug fixable on *either* side (MiMo could strip `propertyNames`; Hermes happens to have a Moonshot sanitizer). This is a **maturity gap, not primitive superiority.** |
| **Llama-3.3-70B drifts off required fields (no enforcement)** | Hermes does **not** enforce; it relies on the model calling the right tool, then `coerce_tool_args` + `_repair` fix *malformed* calls. | **Relocated.** Coerce/repair fixes bad *args*; it does **not** fix the model **not calling the tool at all**. That no-tool-call path is not traced end-to-end and is the same unaddressed gap as the spike's mimo-auto "ignored the forced tool." [UNKNOWN] |
| **DeepSeek 400s** | DeepSeek is named in the coerce layer; native calls + coercion sidestep a forced `response_format` the provider rejects. | **Likely dodged**, by removing the rejected `response_format` param. Unverified head-to-head. |
| **mimo-auto stringifies nested objects / ignores forced tool** | `_repair` handles some malformed JSON; **no** general text-recovery registry exists for the ignored-tool case. | **Partially relocated.** Nested-arg stringification may be repairable; ignoring-the-forced-tool is the same unaddressed no-call gap. |

**The honest synthesis (verdict-aligned):** "hermes-agent uses NO structured output; native function-calling only. The reframe **removes the spike's forced-envelope failures but MOVES fragility to tool-selection plus tool-schema** (per-backend sanitizers); **no hard one-action guarantee. More robust, not free.**" [verdict C3-robustness]. And decisively: **there is no benchmark.** The repo has no head-to-head conformance data proving tool-calls-as-control beats a forced envelope on weak models; Hermes's `tool_choice:required` (anthropic_adapter.py:2386) is the *same* emulated-forcing primitive the MiMo/Venice spike found unreliable. The spike's real decider — whether **vLLM server-side `guided_json`** rescues weak models — is **orthogonal to Hermes's design and still infra-blocked/unmeasured**; Hermes appears **not** to use server-side constrained decoding on its self-host path at all [UNKNOWN but strongly indicated — only `plugin_llm.py` touches `response_format`].

## 5. Reframe for RightClaw

**Mapping the three uses onto tool-call control:**

| RightClaw structured use | Tool-call-control equivalent | Cost |
|---|---|---|
| **(1) REPLY envelope** (content / attachments[] / reply_to / used_skill_receipts[]) | Plain assistant text = reply; attachments via inline `MEDIA:` tokens or a `send_message`-style tool; `reply_to`/receipts as tool args or text affordances | Loses the **single typed object** guarantee. RightClaw's reply is *structured media + threading metadata*, not just text — these become tool args or inline tokens, which weak models may omit (the Llama "drops required fields" risk reappears as "omits `reply_to`"). |
| **(2) CRON/BG notify-vs-silent oneOf + `run_note`** | A `deliver_notify(content, attachments)` tool vs `stay_silent(reason)` tool, **or** the Hermes `[SILENT]` text sentinel | The sentinel is **simpler but lossier**: Hermes has **no structured `run_note`/`reason` co-delivered with a silent decision**. RightClaw's `cron.json` is a genuine `oneOf{notify\|silent}` **with `run_note` required alongside the union** (verified) — a bare sentinel drops that side-channel. Two-tools restores it but reintroduces "did it call exactly one?" |
| **(3) PREFILTER classify** (skip/patch/create + target + reason) | A `classify(decision, target_skill, reason)` tool **or** tolerant free-text JSON (Hermes does both) | This is the **cleanest fit** — a one-shot classify with no media. But it's also the case where a forced single tool-call is *exactly* `tool_choice:required` = the unreliable primitive. Hermes's own classifier sidesteps this by **not forcing** and tolerantly parsing text [C8]. |

**The "force exactly one terminal action per turn" problem — this is the crux.** RightClaw's envelope *guarantees* exactly one well-formed terminal object. Tool-call control gives **no such guarantee**: the model may call zero tools (text-only), multiple tools, or the wrong tool. Hermes accepts this — its loop is multi-step ReAct, terminal on *no* tool-call, with text as the natural reply [verdict C5]. For RightClaw's **delivery decision** (notify vs silent), "exactly one of two outcomes" is a hard product requirement; emulating it with two tools + `tool_choice:required` lands you back on the spike's fragile forcing path. The sentinel approach (text `[SILENT]` else deliver) is the robust escape — *if* you can drop the structured `run_note` side-channel.

**Does it compose with RightClaw's MCP tool layer?** **Yes, and this is the strongest argument *for*.** RightClaw already runs every tool through the MCP aggregator (`mcp__right__*`). Control-as-tool-calls means the reply/deliver/classify decisions become *more MCP tools* — `mcp__right__send_message`, `mcp__right__deliver_notify`/`stay_silent` — riding the exact dispatch path that already works, instead of a parallel `--json-schema` mechanism layered on top. Hermes proves this composes cleanly (messaging *is* a tool, `send_message_tool.py` [verdict 5]). This also removes the `ClaudeInvocation` `--json-schema` invariant's coupling to a single harness.

**Does it reduce the multi-model-fragility risk that gated the harness decision?** **Only for the unforced subset, and unproven even there.** It removes the *forced-`response_format`* failure mode that hard-failed Kimi/small-Qwen/DeepSeek in the spike *for the reply/silent decisions* that need no schema, and it matches what models (especially Hermes fine-tunes) are *most heavily trained for* (function-calling) [claims 4/10]. But for the *forced* classify/deliver decisions it (a) uses `tool_choice:required` = the same primitive the spike broke, (b) relocates fragility to tool-selection + per-model schema sanitization (Moonshot), and (c) requires RightClaw to **build the coerce/repair/sanitizer layer Hermes has and RightClaw does not** — trading hard per-turn schema validation for best-effort+repair+retry, a different correctness contract whose acceptability for RightClaw's *typed* REPLY/DELIVERY control is "an unevaluated product decision."

## 6. Verdict + recommendation

**Verdict: tool-call-as-control is a real, production-proven alternative that a direct peer (hermes-agent) chose specifically to run the open/self-host models RightClaw wants — but the evidence does NOT establish it is more reliable than a forced envelope on weak models. Its reliability advantage is genuine and proven only for the *unforced* decisions (free-text reply, `[SILENT]`-else-deliver). For RightClaw's *forced* decisions (classify, notify-vs-silent-as-two-tools), tool-call control falls back on `tool_choice:required` — the same emulated-forcing primitive the MiMo/Venice spike already found fragile — and buys nothing over the envelope except a parser/sanitizer layer RightClaw would have to build. The one concrete spike failure it "fixes" (Kimi `propertyNames`) is, by the spike's own diagnosis, an injected-keyword tooling bug fixable on either side — a maturity gap, not primitive superiority.**

**Recommendation: a hybrid, not a wholesale switch — and gate it on a spike, exactly as the harness decision was.**

1. **Move use (1) reply and use (2) delivery to native-text + sentinel + tools** — these are where the envelope hurts most across open models and where Hermes's pattern is directly proven and *unforced* (plain text reply [verdict 5]; `[SILENT]` sentinel [verdict C6]). This composes with the existing MCP layer at near-zero new surface and is the low-risk, high-payoff move.
2. **Keep a typed channel where it's cheap and load-bearing** — `run_note`, `used_skill_receipts`, `reply_to` are *metadata* that text+sentinel drops (RightClaw's `cron.json` requires `run_note` alongside the `oneOf`, verified). Carry them as **tool args on a single `deliver`/`reply` tool** (decision = which tool + its args), accepting that this is `tool_choice`-adjacent and must be paired with a recovery/coerce/repair layer.
3. **You will have to build Hermes's robustness layer** — `coerce_tool_args`, `_repair_tool_call_arguments`, per-model schema sanitizers (Moonshot). Note you would be building these *from scratch*; the general text-recovery registry that an earlier draft credited Hermes with **does not exist in Hermes either**, so it is not a borrowable asset. Without this layer, tool-call control is *less* robust than the envelope on exactly the weak models you're optimizing for. This is the honest cost.

**What a spike must test** (the evidence is unanimous that this is unmeasured):
- **`tool_choice:required` on Kimi/small-Qwen** — does forcing a single classify-tool hit the *same* enforcement-engine wall the `--json-schema` envelope did (after stripping injected keywords like `propertyNames`), or does the model emit the call natively? This is make-or-break: if `required` reproduces the spike failures, tool-call control only helps the *unforced* reply/silent cases, not the *forced* classify/deliver ones.
- The **no-tool-call / off-spec** failure on a native-FC provider — does Llama-3.3-70B / mimo-auto *call* `deliver_notify` reliably, or drift to text? (The one path Hermes's coerce/repair does **not** cover.)
- **vLLM server-side `guided_json` vs no-enforcement tool-call** head-to-head — the spike's stated real decider, still infra-blocked, orthogonal to Hermes (which uses neither). This determines whether RightClaw's self-host path can have *both* structure and robustness.

**Bottom line:** Hermes validates the *primitive* (tool-calls + text + sentinel, no forced envelope) as a production choice for multi-model robustness, and it composes cleanly with RightClaw's MCP layer. But its reliability win is confined to the *unforced* reply/silent decisions; for the *forced* classify/deliver decisions it reduces to `tool_choice:required` — the same primitive the spike found fragile — plus a coerce/repair/sanitizer layer RightClaw would have to build itself. It offers **no hard one-terminal-action guarantee** and is **not benchmarked** to beat the envelope on weak models. Adopt it for reply + silent (low risk, high payoff, proven); spike `tool_choice:required` for the forced classify/deliver decisions before committing.
